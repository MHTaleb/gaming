# Publishing Packet Defense to Google Play

Everything below is either **done in this repo** (with the file that does it) or
**something only you can do** (Play Console, accounts, money). The distinction is
the point of this document — a green checklist that hides three manual steps is
worse than no checklist.

---

## 1. The three things that silently earn $0

These are the ones that fail *quietly*: the game runs, ads appear, nothing errors,
and the revenue is zero.

| # | What | Where | Status |
|---|---|---|---|
| 1 | AdMob **app id** is Google's public test id | `capacitor.config.json` → `plugins.AdMob.appId` | ⚠️ test id |
| 2 | All three **ad unit ids** are Google's public test ids | `www/js/config.js` → `ads.android` / `ads.ios` | ⚠️ test ids |
| 3 | **Purchase validation is switched off** | `www/js/config.js` → `validator.url` is `''` | ⚠️ off |

Test ads look completely real. They serve, they render, they pay nothing. If you
read only one section of this file, read this one.

### 1a. AdMob application id

`capacitor.config.json`:

```json
"plugins": { "AdMob": { "appId": "ca-app-pub-XXXXXXXXXXXXXXXX~YYYYYYYYYY" } }
```

Then `npm run android:prepare`. **`tools/harden-android.js` is what makes this
take effect**: `@capacitor-community/admob` v7 does not read the Capacitor config
block at all — it reads the Android meta-data
`com.google.android.gms.ads.APPLICATION_ID`, which has to resolve from a string
resource. The harden script writes `res/values/admob.xml` and injects the
meta-data into the manifest, because `android/` is generated by `cap add android`
and gitignored, so there is no committed manifest to edit by hand.

Until that id is replaced the script prints a loud warning on every run.

### 1b. Ad unit ids

`www/js/config.js`:

```js
ads: {
  android: {
    banner:       'ca-app-pub-XXXXXXXX/BBBBBBBBBB',
    interstitial: 'ca-app-pub-XXXXXXXX/IIIIIIIIII',
    rewarded:     'ca-app-pub-XXXXXXXX/RRRRRRRRRR',
  },
  ios: { /* same three, separate ids */ },
}
```

Create three ad units per platform in AdMob (banner, interstitial, rewarded).

### 1c. Turn purchase validation on

The validator in `server/validator/` verifies a purchase against Google's API
before anything is granted. With `validator.url` empty the client grants from its
own local receipt — `www/js/purchases.js` returns early with
`{ ok: !required, unverified: true }`, and nothing inspects `unverified`.

1. Deploy the validator (see `server/validator/README.md`) and set its env:
   `APP_ID`, `PACKAGE_NAME`, `PRODUCTS`, `SIGNING_KEY`, `GOOGLE_SERVICE_ACCOUNT`.
2. Put its URL and its Ed25519 public key into `www/js/config.js` and set
   `required: true`.
3. **Add the validator origin to the CSP** in `www/index.html`:

```
connect-src 'self' https://your-validator.example.com
```

Step 3 is not optional and is easy to miss: the current policy is
`connect-src 'self'`, so with the URL configured the request is blocked by the
WebView and *every purchase fails* — a worse outcome than leaving it off.

## 2. Play Console: products, and where the money lands

**Money reaches you through Google Play, not through this app.** The app never
sees a card, a bank account or a payout address: Google collects, keeps its cut,
and pays out to the merchant account attached to the Play developer account.
Nothing in this repository can change where money lands — that is set in
**Play Console → Payments profile**.

Create these four products in **Play Console → Monetise → Products → In-app
products**. The ids must match `www/js/config.js` **exactly** — the app asks for
these ids and grants nothing it cannot find:

| Product id | Type | Grants |
|---|---|---|
| `remove_ads` | one-time (non-consumable) | suppresses banners and interstitials |
| `coins_small` | consumable | +500 credits |
| `coins_medium` | consumable | +1,600 credits |
| `coins_large` | consumable | +5,000 credits |

> Prices live in Play Console, not in the code. The numbers in `config.js` are
> display fallbacks for when the store cannot be reached; if Play has no product,
> the shop shows a fallback price and the purchase fails.

`SECURITY.md` has a checkbox for this; it is still unchecked in the repo, which is
correct — it cannot be done from a terminal.

## 3. Policy: the forms that block review

| Requirement | Why | Where to answer |
|---|---|---|
| **Privacy policy URL** | mandatory for every app; must be publicly reachable | Play Console → App content. Text to host: `docs/PRIVACY.md` |
| **Ads declaration** | the app contains ads | App content → Ads |
| **Data safety form** | must declare what is collected and shared | App content → Data safety. Use `docs/PRIVACY.md` §"Data safety answers" |
| **Content rating** | questionnaire; this game is fantasy violence against software, no user content | App content → Content rating |
| **Target API level** | **BLOCKING, and the deadline has passed.** Since 31 August 2026 new apps and updates must target **Android 16 (API level 36)**. Capacitor 7 targets API 35, so an upload today is rejected. Capacitor 8 sets `compileSdk`/`targetSdk` 36 (`minSdk` 24) and requires Node 22+. An extension to 1 November 2026 can be requested in Play Console. See **PD-101**, and **R-01** in `docs/RESEARCH.md`. | build config — `npx cap sync` after upgrading |
| **App access** | all content is reachable without login, so "all functionality available without restrictions" | App content → App access |

> **Why this row says what it says.** It previously read "Capacitor 7 defaults to
> `targetSdk 35`, which meets it — no action unless you pin it lower". That was
> true when it was written and became false on 31 August 2026, and nothing in the
> repository recorded when the claim had last been checked. It is now dated and
> cites the research entry behind it. If you are reading this more than a few
> months after 2026-09-19, re-read the source before trusting it: **R-01**.

**Permissions actually requested:** `INTERNET` (Capacitor) and
`com.android.vending.BILLING` (from `cordova-plugin-purchase`). The manifest is
hardened by `tools/harden-android.js`: `allowBackup=false`, no cleartext traffic,
network security config, no debuggable flag. `android:debuggable="true"` is
stripped on every prepare, which matters because a debuggable release build is
both a security hole and a Play review flag.

## 4. Signing

`tools/configure-signing.js` patches `android/app/build.gradle` to add a release
`signingConfig` that reads four **environment variables** — the keystore and its
passwords are never written into a file in this repo:

```
KEYSTORE_PATH   KEYSTORE_PASSWORD   KEY_ALIAS   KEY_PASSWORD
```

The keystore itself is excluded from version control by `packet-defense/.gitignore`
(`*.keystore`, `*.jks`).

```bash
export KEYSTORE_PATH=/absolute/path/to/upload.keystore
export KEYSTORE_PASSWORD=...
export KEY_ALIAS=upload
export KEY_PASSWORD=...
npm run android:bundle      # → android/app/build/outputs/bundle/release/app-release.aab
```

Use **Play App Signing** (the default): you upload with your upload key, Google
holds the app signing key. If you lose the upload key you can have it reset; if
you opt out and lose the signing key, you cannot update the app.

## 5. Version numbers

`versionCode` and `versionName` are **not set anywhere in this repo** — Capacitor
generates a default `app/build.gradle` with `versionCode 1`. Play rejects an
upload whose `versionCode` is not higher than the live one.

Before each upload, in `android/app/build.gradle`:

```gradle
defaultConfig {
    versionCode 2          // must strictly increase, every single upload
    versionName "1.0.1"    // free-form, this is what users see
}
```

`android/` is gitignored, so this is per-machine. If you intend to ship often,
move these into `tools/harden-android.js` so a number cannot be forgotten.

## 6. Store listing assets (you must supply these)

| Asset | Requirement | Where it comes from |
|---|---|---|
| App icon | 512 × 512 PNG, 32-bit, no alpha | `npm run assets` |
| Feature graphic | 1024 × 500 PNG/JPG | `npm run assets` |
| Phone screenshots | 2–8, at least 320px on the short side | `npm run shots` |
| Short description | ≤ 80 characters | not written yet — PD-109 |
| Full description | ≤ 4000 characters | not written yet — PD-109 |

### Screenshots

`npm run shots` writes five 1920×1080 PNGs into `store/screenshots/`, along
with a manifest recording what each one shows. They are captured from the real
build by `tools/screenshots.js`: a headless Chromium drives the actual game, so a
screenshot cannot show something the game does not do, and re-running the tool
after a change to the palette or the HUD regenerates all five.

| File | What it shows |
|---|---|
| `01-board.png` | Act 11 mid-wave on Insane, thirty towers, one of every type |
| `02-briefing.png` | The same ticket's briefing: the premise, the threat list, the tip |
| `03-coop.png` | A co-op lobby with two real players in it |
| `04-victory.png` | The results screen for the ticket in shot one |
| `05-title.png` | The menu |

The order is the order to upload them in — the first two are what a browsing
player actually looks at. Capture refuses to write a file if it can find a
placeholder package id, a debug value, a TODO or an ad test unit in the text on
screen, including text the canvas drew, and `node tools/screenshots.js --check`
proves the set is complete and not blank without needing a browser.

## 7. Release order

1. `npm run android:prepare` (syncs `www/`, then hardens `android/`)
2. `npm run android:bundle`
3. Play Console → **Internal testing** → upload the `.aab` → add yourself
4. Install from the Play link on a real device and check the three things a
   browser cannot tell you:
   - a real **banner** appears on the menu (not a test banner — check AdMob)
   - a real **interstitial** appears after the third clear
   - the **rewarded** offer on the results screen pays credits
   - a **real purchase** completes and the entitlement survives a reinstall
5. Promote to closed/open testing, then production
