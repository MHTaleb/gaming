# ARCHITECTURE.md — runtime architecture and conventions

> This documents the **actual** code in `Assets/_Game/Scripts`. If code and doc disagree, fix one —
> don't quietly diverge. Read `AGENTS.md` first for the workflow contract.

## Assembly layout

| Assembly | Path | Purpose |
| --- | --- | --- |
| `GladToSeeYou.Runtime` | `Assets/_Game/Scripts` | all gameplay + services. **No `UnityEditor` references.** |
| `GladToSeeYou.Editor` | `Assets/_Game/Editor` | bootstrap, project setup, build helpers, asset validation |
| `GladToSeeYou.Tests.EditMode` | `Assets/_Game/Tests/EditMode` | logic tests (damage math, state machine, input pipeline) |
| `GladToSeeYou.Tests.PlayMode` | `Assets/_Game/Tests/PlayMode` | scene-level smoke tests via `VerticalSliceFactory` |

Runtime references: `Unity.InputSystem`, `Unity.AI.Navigation`, `UnityEngine.UI`,
`Unity.RenderPipelines.Core.Runtime`, `Unity.RenderPipelines.Universal.Runtime`.

## Composition, not god objects

`GameRoot` is the **composition root** (one per scene): creates/registers services
(`AudioService`, `VFXService`, `QualityProfileService`, `HitStopService`, `InputRouter`, `SaveService`)
and exposes them via a tiny static registry. It contains no gameplay logic itself.

Gameplay objects are **modular components on a root object** that reference each other explicitly:

```
PlayerRoot
 ├─ PlayerInputReader      (device-agnostic, produces InputCommands)
 ├─ PlayerMovement         (CharacterController, camera-relative; owns gravity/rotation only)
 ├─ PlayerDodge            (i-frames + dodge state; asks Movement for the burst)
 ├─ PlayerCombat           (attack chains from WeaponData; toggles WeaponHitbox windows)
 ├─ PlayerHealth           (wraps Health; invulnerability, hit-stun signaling)
 ├─ PlayerAnimation        (consumes state → IAnimationDriver)
 ├─ PlayerTargeting        (lock-on candidate search among Targetable)
 └─ PlayerAbilities        (ability slots from AbilityData; cooldowns)
```

`EnemyRoot` mirrors this: `EnemyBrain` (state machine) + `EnemySensor` + `EnemyLocomotion` +
`EnemyCombat` + `EnemyHealth` + `EnemyAnimation`.

## Events, not webs of references

`EventBus` (static, typed, struct payloads) is the sanctioned global channel. Used for *reactions*:
damage feedback, hit-stop requests, death notifications, camera impulses, HUD updates.
**Gameplay *decisions* still flow through direct references** (movement asks its own state), because
event-driven gameplay state machines are harder to reason about and debug.

`CombatFeedback` is the *only* class that translates damage events into screenshake/VFX/SFX/numbers —
that's the deliberate boundary between **gameplay damage logic** and **visual effects**.

## Data: ScriptableObjects, not constants

`PlayerStats`, `WeaponData`, `EnemyData`, `AbilityData`, `VFXData`, `AudioEvent`, `QualityProfileData`
live in `Assets/_Game/Scripts/ScriptableObjects/` and are instantiated by the bootstrap into
`Assets/_Game/Settings/Generated/` with sane defaults. Gameplay classes read them via `[SerializeField]`
references. **Never hard-code tuning numbers in gameplay classes.**

## Deterministic bootstrap (important!)

The vertical slice is **generated by code**, not hand-authored scene files:

- `VerticalSliceFactory.BuildContent(...)` constructs arena, hero, enemy, camera rig, HUD, mobile controls,
  lighting, volume profile — using only primitives, procedural materials, procedural audio.
- The editor menu `Glad to See You ▸ Bootstrap ▸ 2. Build Vertical Slice Scene` wraps it and saves a scene.
- PlayMode tests call the **same factory** — tests and the shipped slice can't drift apart.

Why: reproducible scenes, reviewable diffs, a scene that can't be "fixed by clicking" into an unknowable state.
Real art gets swapped in by replacing the *placeholder visuals* (child objects), which is why every system
finds its visuals through serialized references, not `GetComponentInChildren` chains.

## Input

Modern Input System, **code-built action maps** (`InputActionLibrary`) — one source of truth, no GUID assets
to corrupt; the bootstrap can *export* an equivalent `.inputactions` asset for inspection.
`InputRouter` merges two providers that both produce `InputCommands`:
`PlayerInputReader` (keyboard/mouse/gamepad via actions) and `VirtualInputLayer` (on-screen stick/buttons).
Gameplay code only ever sees `InputCommands`. Editor play = keyboard/gamepad; device = touch. Same code path.

## Camera

`ThirdPersonCameraRig` is a custom, mobile-cost-aware solution (evaluated Cinemachine 3; rejected for now:
extra runtime cost + asset-authoring in bootstrap). Provides: orbit with smoothing, collision via
sphere-cast solver, lock-on framing, impulse (shake) offsets, touch drag support, sensitivity settings.
Swap-in of Cinemachine later is an option; the rig exposes the same "target + orbit + impulse" concepts.

## Animation

`IAnimationDriver` separates *what should be shown* from *how*:
- `ProceduralAnimationDriver` (default placeholder): squash/stretch, lean, swing arcs, dodge roll, hit flinch —
  so the slice is fully animated **without any assets**.
- `AnimatorAnimationDriver`: drives a real Animator (parameters in `AnimationParameters`) once
  humanoid clips exist. See `ANIMATION_PIPELINE.md` for the retargeting plan.

## Audio / VFX

- `AudioService`: pooled one-shots + music; `PlaceholderAudioFactory` synthesizes clips at startup
  (hit/whoosh/step/death) so sound design slots exist before assets arrive.
- `VFXService`: pooled `ParticleSystem` one-shots configured from `VFXData`; default archetypes
  (hit spark, dust, death burst) are code-built. Shader: URP Particles/Unlit.

## Quality & settings

`QualityProfileService` maps `Low/Balanced/High` to: target frame rate (30/60/60), shadow distance,
pixel light count, URP render scale. `SaveService` persists profile + sensitivity + volumes (PlayerPrefs-based).

## Dependencies & why

| Package | Why it's here |
| --- | --- |
| `com.unity.render-pipelines.universal` | The mobile render pipeline. Non-negotiable. |
| `com.unity.inputsystem` | Required for gamepad + touch parity and the modern input architecture. |
| `com.unity.ai.navigation` | NavMeshSurface/Agent for enemy locomotion (single arena; baked once). |
| `com.unity.test-framework` | Doctrine: logic is tested. EditMode + PlayMode suites. |
| `com.unity.ugui` | HUD/mobile controls via uGUI (no TMP dependency for placeholders — avoids essentials friction). |

Adding anything else requires a "why" in the commit message (see `AGENTS.md`).

## Conventions cheat-sheet

- Namespaces: `GladToSeeYou.Core`, `.Player`, `.Combat`, `.AI`, `.Camera`, `.Input`, `.Animation`, `.UI`, `.Audio`, `.Save`, `.Utilities`, `.Data`.
- Layers: `Player`, `Enemy`, `Ground`, `Hitbox`, `Camera` — created by the bootstrap; never hard-code indices.
- Physics: non-alloc queries in per-frame paths; hitboxes are sphere queries, not per-frame trigger spam.
- Update philosophy: systems own their own `Update`; no central "manager tick" that fans out.
